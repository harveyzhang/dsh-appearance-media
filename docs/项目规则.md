# 项目规则

> 这些规则不是风格偏好，**每一条都对应一次真实事故**。
> 每条规则后面写着「谁在管它」——一条没有自动检查兜着的规则，迟早会被人忘。

## 完成的定义

```bash
node tools/verify-release.mjs      # 默认模式：两分钟内
node tools/verify-release.mjs --full   # 加上陌生人验收（克隆到临时目录再跑一遍）
```

**★ 这条命令全绿，才算做完。** 没有它，就只是"我改完了"。

---

## 规则 1 · 声称即断言：文档里的每一句事实都要能被机器核对

**为什么**（真实事故，三起同一类）：
- README 暗示"发到 npm 就会出现在插件市场里"——**错的**：市场的索引是
  `awesome-dsh-plugin.com/plugins.json`，由官方列表仓库的 `data/plugins/*.yml` 生成，
  不是实时搜 npm。⇒ 文档在承诺一件不会发生的事。
- `skills/dsh-appearance-media-install/SKILL.md` 写"已发布到 npm"——**假的**（registry 404）。
  ⇒ **agent 照着这句做会 404。**
- 官方目录的 `icon` 指向 SVG——官方明写"icon 必须是位图，SVG 会被拒绝"⇒ 会被 CI 打回。

**怎么做**：凡是**关于现在的事实**（已发布/已收录/已支持/某地址可达），
要么不写，要么让机器去核。**不许靠记忆写状态。**

**谁在管**：`node tools/verify-docs.mjs`（从文档里读出它声称了什么，再和真实世界核对）。

---

## 规则 2 · 每条断言都必须能变红

**为什么**（真实事故）：
- `verify-remux.mjs` 的 57 条核心检查被包在 `if (existsSync(夹具))` 里，夹具只在这台机器上有
  ⇒ 别人克隆下来只看到「1 check(s), 0 failed」——**一片绿，什么都没验**。
- 一条"仓库自包含性"护栏被我插进了 `for` 循环体里 ⇒ 平时压根不跑 ⇒ 测试它是绿的才发现是死的。
- 一个"只认字面量"的白名单让遮罩一调深就红 ⇒ 逼着人改断言来迁就实现。

**怎么做**：
- 写完一条断言，**自己造一个反例**（改副本，不动真文件），**看到它变红**才算写完。
- 断言不得依赖"这台机器上碰巧有的东西" ⇒ 夹具随仓库走。
- 环境缺东西时，**跳过（SKIP）并写明理由**，不要伪装成通过，也不要伪装成失败。
- 检查器的断言总数必须 > 0（防止"什么都没检查"）。

**谁在管**：每套断言的 `--negative` 反向对照；`verify-package.mjs` 的反向对照。

## 规则 3 · 仓库必须自包含

**为什么**（真实事故）：两套断言把夹具放在仓库外的 `.sdd/` 目录
⇒ **全新克隆里 ENOENT 崩掉**，别人根本没法跑我们的测试。

**怎么做**：测试要用的东西一律放进仓库（`tools/fixtures/`）；
真素材只认环境变量（如 `DSHAM_REMUX_TAIL`）；不许出现指向别人家目录的路径。

**谁在管**：`verify-package.mjs` 的「没有任何套件去仓库外面找素材」；
`verify-release.mjs --full` 的陌生人验收（克隆到临时目录跑一遍）。

---

## 规则 4 · 改动之前先声明写范围；动别人正在改的文件之前先读最新内容

**为什么**（真实事故）：
- 一个 agent 正在改 `src/client.js`，我同时改它 ⇒ 套件跑到一半文件变了 ⇒ **假红**，
  白排查半小时。
- 两个 agent 同改 `package.json` ⇒ 互相覆盖。
- 一次并发编辑让 `verify-remux` 跑了 16 分钟。

**怎么做**：
- 每个 agent 的 brief 里写死**写范围**（哪些文件能碰、哪些不能）。
- 动一个**可能有人在改**的文件前：先读最新内容，用带唯一锚点的编辑，**不整文件覆盖**。
- 看到"红灯但代码看着没问题" ⇒ **先怀疑并发编辑**（`verify-release.mjs` 会直接告诉你
  哪些文件在测试期间被改过）。

**谁在管**：`verify-release.mjs` 的并发编辑检测。

---

## 规则 5 · 改文件用精确工具，不要用字符串手术

**为什么**（真实事故）：我用 python 字符串替换去改一个断言文件，
把一段 `for` 循环的头切掉了 ⇒ **文件通过了 `node --check`（因为注释挡着），逻辑却坏了**，
跑出来是"崩了"，白排查。

**怎么做**：
- 改文件用**编辑工具**（精确替换）或**整文件重写**；不用 python/sed 去做字符串手术。
- 改完立刻：`node --check` **＋ 跑一遍看真实输出**（两者都要，缺一不可）。
- 删东西前先确认它是什么：符号链接不能 `rm -rf` 目标、目录不能靠 `ls` 的结果猜。

---

## 规则 6 · 沙箱和工具的边界要先查，不要试错

**为什么**（真实事故）：本机的安全网会拦 `rm -rf`（cwd 外）和 `git checkout <path>`（会丢改动），
我试错了几次，白费回合；而且 `git checkout` 那次差点丢掉另一个 agent 的改动。

**怎么做**：
- 删除：只删**明确的路径**，优先 `rm -f` 单文件或先 `mv` 到临时目录。
- 回退一个文件：`git show HEAD:<path> > <path>`（**不是** `git checkout <path>`）。
- 批量测试一律加 `timeout`（这个项目有过一套跑了 16 分钟）。

---

## 规则 7 · 界面问题要去量，不要靠截图猜

**为什么**（真实事故）：截图上看着"单选圆点压住了素材名"，
**量下来** radio x=388、名字 x=411、每行都一样 ⇒ 布局本来是对的，
那个"重叠"是**弹窗太透明、背面的字透上来**造成的错觉。
⇒ 我差点去改一个没坏的布局。

**怎么做**：视觉问题先在真机上量（getBoundingClientRect / 计算样式），
确认是布局问题还是别的原因，再动手。

---

## 规则 8 · 装完之后必须真的跑起来看一眼

**为什么**（真实事故）：桌面 profile 由桌面应用独占，命令行 `dsh plugin add` 会直接报错；
而且**宿主在启动时固化插件代码清单** ⇒ 改完不重启，界面纹丝不动，
很容易被误判成"装失败了"。

**怎么做**：
- 装插件走宿主自己的工具（`plugin_manager` 的 `install_bundle`），不要用 shell 复刻安装步骤。
- 装完**重启宿主**，再验证：请求插件自己的路由（返 200 = 宿主半侧活着，404 = 没挂上）。
- 客户端半侧要**在真浏览器里点一遍**（隔离宿主 + Playwright），光看断言不算。

---

## 规则 9 · 第三方代码进来要留出处

**为什么**：片头与屏保的实现来自开源项目 `dsh-boot-animation`（MIT）。

**怎么做**：版权声明保留在 `THIRD_PARTY_NOTICES.md` 和源文件头；
**★ 内部代号（P05 之类）不许出现在用户能看到的文字里** —— 用户看到的是插件详情页
（`docs/DETAIL.md`）和 README。

**谁在管**：`verify-docs.mjs`（商标声明必须一字不差地在场）。
